# Инварианты preserving DOM

Документ — источник истины для вехи **M6** (preserving DOM). Он описывает, что
дерево обязано сохранять и почему, и опирается на измерения корпуса
(43 файла, **569 XML-частей**; разбор — ручной, побайтовый). ZIP-уровень описан
отдельно в [`zip-fidelity.md`](zip-fidelity.md), происхождение корпуса —
в [`corpus.md`](corpus.md).

Целевое свойство M6:

```
serialize(parse(bytes)) == bytes   для всех 569 XML-частей корпуса
```

и, что важнее, **устойчивость к повторению**:

```
serialize(parse(serialize(parse(bytes)))) == serialize(parse(bytes))
```

Второе свойство ломается ровно теми способами, которые описаны в §3.

## 1. Инвариант покрытия

Узел дерева хранит не «содержимое», а **спан** — полуинтервал `[start, end)`
в исходном буфере части. Дерево — это разметка буфера, а не его копия.

**И1 (покрытие корня).** Спаны узлов верхнего уровня, взятые в порядке
следования, плотно покрывают весь буфер:

```
top[0].start == 0
top[i].end   == top[i+1].start   для всех i
top[last].end == bytes.len()
```

**И2 (покрытие внутренности).** Для любого элемента `e`, записанного парой
тегов, спаны его детей плотно покрывают промежуток между концом открывающего
и началом закрывающего тега:

```
e.children[0].start == e.open_tag.end
e.children[i].end   == e.children[i+1].start
e.children[last].end == e.close_tag.start
```

**И3 (отсутствие наложений).** Из И1 и И2 следует, что никакие два спана
братьев не пересекаются и между ними нет ни одного непокрытого байта.

**И4 (всё — узел).** Любой байт файла принадлежит ровно одному узлу.
Поэтому узлами являются не только элементы:

| что | почему отдельный узел |
| --- | --- |
| XML-декларация | форм четыре (§2.1), реконструировать нельзя |
| перевод строки после декларации | форм четыре, включая одиночный `\r` (§2.3) |
| пробелы между тегами | 20 различных форм в корпусе (§2.6) |
| текст элемента | стиль экранирования не восстановим (§2.7) |
| комментарий `<!-- -->` | в корпусе не встречается, но допустим форматом |
| PI, кроме декларации | в корпусе не встречается |
| CDATA | в корпусе не встречается |
| DOCTYPE | **запрещён** политикой безопасности ядра — при встрече ошибка, а не узел |
| BOM | 16 частей корпуса (§2.2) |

Комментарии, PI и CDATA корпусом **не покрыты** — измерено: 0 частей из 569
содержат `<!--`, 0 содержат `<![CDATA[`, 0 содержат PI кроме декларации,
0 содержат `<!DOCTYPE`. Это дыра в покрытии, а не разрешение их не
поддерживать: их обязаны закрыть синтетические тесты вехи M6.

**И5 (сериализация тривиальна).** Если И1–И4 выполнены, сериализация
нетронутого дерева — это конкатенация спанов в порядке обхода, то есть
`bytes[0..len]`. Побайтовое совпадение получается по построению, а не
благодаря аккуратному переписыванию каждой лексемы.

**И6 (локальность правки).** Изменение узла заменяет его спан на новые байты.
Спаны всех остальных узлов остаются валидными относительно **исходного**
буфера; сериализатор склеивает куски исходника и вставки. Один изменённый
атрибут не переписывает документ.

## 3. Экранирование нового содержимого

Правило касается **только** байтов, которые пишет наш код: значение, поданное
пользователем в API. Существующие байты не трогаются никогда (§4).

### 3.1 Правило

В **тексте** элемента экранируются:

| символ | во что | почему |
| --- | --- | --- |
| `&` | `&amp;` | иначе начинается ссылка на сущность |
| `<` | `&lt;` | иначе начинается тег |
| `>` | `&gt;` | не обязательно по XML, но обязательно внутри `]]>`; экранируем всегда — дешевле, чем анализировать контекст |
| `\r` (U+000D) | **`&#xD;`** | см. §3.2 |

В **значении атрибута** экранируются те же четыре плюс ещё три:

| символ | во что | почему |
| --- | --- | --- |
| `"` | `&quot;` | мы всегда пишем новые атрибуты в двойных кавычках |
| `\r` (U+000D) | **`&#xD;`** | см. §3.2 |
| `\n` (U+000A) | **`&#xA;`** | см. §3.2 |
| `\t` (U+0009) | **`&#x9;`** | см. §3.2 |

### 3.2 Почему `\r`, `\n`, `\t` обязаны стать числовыми ссылками

XML 1.0 предписывает два преобразования, которые происходят **при разборе**,
до того как значение попадёт в приложение.

**Нормализация переводов строк (XML 1.0, §2.11).** Процессор обязан заменить
в разобранной сущности каждую последовательность `\r\n` и каждый одиночный
`\r` на `\n` — везде: и в тексте, и в атрибутах. Литеральный `\r` в файле
после разбора не существует. **Числовая ссылка `&#xD;` под это правило не
попадает**, потому что нормализация применяется к литеральным байтам, а
ссылки раскрываются после неё.

**Нормализация значения атрибута (XML 1.0, §3.3.3).** Для значения атрибута
процессор дополнительно заменяет каждый символ `#x9`, `#xA`, `#xD` на пробел
`#x20`. И снова: **на числовые ссылки это правило не распространяется** —
раскрытая ссылка `&#xA;` даёт символ, который в значение попадает как есть.

Следствие. Пусть пользователь просит записать в атрибут строку `"a\tb"`.

- Если мы напишем литеральный таб: файл содержит `attr="a<TAB>b"`. Первый
  round-trip даёт байты, совпадающие с нашим выводом. Но когда эти байты
  разберут снова (наш парсер, Word, LibreOffice — всё равно кто),
  значением атрибута станет `"a b"`. Третье сохранение запишет `attr="a b"`.
  **Второй round-trip разошёлся с первым**: `serialize(parse(x)) != x`
  для `x`, который мы сами и произвели. Тест M6 на устойчивость к повторению
  падает, причём не сразу, а на второй итерации — самый неприятный класс
  дефектов.
- Если мы напишем `attr="a&#x9;b"`: разбор даёт ровно `"a\tb"`, сериализация
  снова даёт `&#x9;`. Неподвижная точка достигнута с первого раза.

Для `\r` в **тексте** ситуация та же, но по правилу §2.11: литеральный `\r`
после разбора превратится в `\n`, и байты разойдутся. `&#xD;` переживает разбор.

Для `\n` и `\t` **в тексте** экранирование не нужно: §2.11 не трогает `\n`,
§3.3.3 к тексту не применяется. Экранировать их всё равно не запрещено, но
это лишний шум, и мы этого не делаем.

### 3.3 Корпус подтверждает, что случай не гипотетический

| подтверждение | измерение |
| --- | --- |
| в реальных файлах в значении атрибута встречаются литеральные `\r` и `\n` | **7 и 7** в `40250030_01.docx` (`w:tooltip` у `w:hyperlink`, 7 тегов с переводом строки внутри) |
| в реальных файлах используется `&#xA;` в тексте — ровно тот приём, который мы кодифицируем | **127 вхождений** в 6 файлах |
| одиночный `\r` как перевод строки в реальных файлах | **110 вхождений** в 110 частях, 9 файлов |

Первая строка — прямое доказательство: эти 7 атрибутов **нельзя** прочитать
в `String` и записать обратно. Их сохранит только спан. Вторая и третья строки
показывают, что оба состояния — «литеральный `\r`» и «`&#xA;`» — реально
сосуществуют в корпусе, и различить их можно только на уровне байтов.

### 3.4 Чего правило не делает

- Не выбирает «красивую» форму: `&#38;` мы никогда не пишем, всегда `&amp;`.
  Это допустимо, потому что правило применяется только к **новому** содержимому,
  у которого нет прошлой формы.
- Не проверяет, что символ вообще допустим в XML 1.0. Управляющие символы
  U+0000…U+0008, U+000B, U+000C, U+000E…U+001F в XML 1.0 запрещены даже в виде
  числовых ссылок; API обязан отвергать такую строку ошибкой, а не пытаться
  её закодировать.
- Не нормализует Unicode и не трогает суррогаты — вход уже `&str`, то есть
  валидный UTF-8.

## 4. Почему существующее содержимое никогда не переэкранируется

Правило §3 — функция от `&str` к байтам. Существующее содержимое `&str` не
является: оно является спаном. Пути от спана к правилу §3 в коде нет.

Формально: узел текста и значение атрибута хранят `Span`. Чтобы применить §3,
нужно сначала получить `String` — то есть **раскрыть** сущности. Такой шаг
существует только в читающем API (`text()`, `attr()`), и его результат
никогда не попадает обратно в сериализатор: сериализатор для нетронутого узла
пишет `&bytes[span]`.

Что это даёт на измеренных данных:

| если бы переэкранировали | что сломалось бы |
| --- | --- |
| `&#34;` → `&quot;` | 44 вхождения в `40250030_01.docx` |
| `&#62;` → `&gt;` | 3 вхождения |
| `&#60;` → `&lt;` | 3 вхождения |
| `&#160;` → литеральный U+00A0 или `&#xA0;` | 1 вхождение |
| `&#xA;` → литеральный `\n` | 127 вхождений в 6 файлах — и это ещё и меняло бы смысл после повторного разбора |
| `<a></a>` → `<a/>` | **104 911 вхождений** в 34 файлах |
| `<a />` → `<a/>` | 181 вхождение |
| `w:customStyle = "1"` → `w:customStyle="1"` | 39 вхождений |
| `<w:rFonts  w:ascii=…` → один пробел | 31 вхождение |
| CRLF → LF | 204 части целиком |
| одиночный CR → LF | 110 частей |

Суммарно «нормализующий» сериализатор разошёлся бы с исходником в **большинстве
из 569 частей**, причём в 34 файлах — на сотнях тысяч байтов.

**Инвариант.** Единственный источник новых байтов — правило §3, применённое к
значению, которое пользователь передал явно. Всё остальное — спаны. Между этими
двумя мирами нет неявного перехода.
