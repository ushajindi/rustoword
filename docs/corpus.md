# Корпус

Корпус — это набор настоящих `.xlsx` и `.docx`, на которых проверяется
центральное свойство проекта: открыть чужой файл, изменить одну ячейку,
сохранить — и не потерять ничего. Синтетические файлы для этого не годятся:
они содержат ровно то, что мы уже умеем, и потому ничего не проверяют.

**Состав:** 43 файла — 20 `.xlsx` и 23 `.docx`, суммарно **606 ZIP-записей**
(569 XML-частей и 37 не-XML), от **шести различимых producer'ов**.

Измерения по корпусу, на которые опираются вехи M2/M3 и M6, лежат в
[`zip-fidelity.md`](zip-fidelity.md) и [`dom-invariants.md`](dom-invariants.md).

---

## 1. Почему корпуса нет в репозитории

Это **реальные документы пользователя**. Они содержат имена, названия
организаций, содержимое рабочих таблиц и договоров; в `docProps/core.xml`
у 30 файлов из 43 записаны настоящие ФИО авторов и правивших. Класть такое
в публичный git — утечка, а не тест-фикстура.

Поэтому:

```
# .gitignore
crates/ooxml/tests/corpus/xlsx/
crates/ooxml/tests/corpus/docx/
crates/ooxml/tests/corpus/MANIFEST.tsv
```

В репозитории остаются только каталог `crates/ooxml/tests/corpus/synthetic/`
(файлы, которые мы производим сами и имеем право публиковать) и этот документ.

Путь к корпусу берётся из переменной окружения **`OOXML_CORPUS`**; при её
отсутствии используется `crates/ooxml/tests/corpus` относительно
`CARGO_MANIFEST_DIR`. Если каталога нет — тесты, зависящие от корпуса,
**печатают предупреждение и проходят**, а не падают. Иначе `cargo test` на
чистой машине был бы красным без причины.

`MANIFEST.tsv` тоже вне репозитория: имена файлов уже говорят о содержимом
больше, чем стоит.

## 2. `MANIFEST.tsv`

Колонки: `file`, `sha256`, `producer`, `entries`, `made_by`, `flags`, `notes`.

`sha256` фиксирует ровно те байты, на которых меряли: если файл подменили или
пересохранили, все числа в `zip-fidelity.md` и `dom-invariants.md` перестают
относиться к делу. Тест M3 обязан сверять хеш до сравнения round-trip'а —
иначе провал будет выглядеть как дефект писателя, хотя это подмена фикстуры.

Колонка `producer` — **метка происхождения XML**, а не контейнера. Это разные
вещи, см. §4.

## 3. Producer'ы

Идентификация — по измеряемым признакам: `docProps/app.xml`, namespace'ы в
корневом элементе, форма XML-декларации, отпечаток ZIP-контейнера.

| метка | файлов | что это на самом деле | по каким признакам определено |
| --- | ---: | --- | --- |
| `excel365` | 11 xlsx | Microsoft Excel, `AppVersion` 16.0300 | `<Application>Microsoft Excel</Application>`; namespace `xr:uid` (Excel revisions) |
| `word365` | 6 docx | Microsoft Office Word, `AppVersion` 16.0000 | `<Application>Microsoft Office Word</Application>` |
| `gsheets` | 5 xlsx | Google Sheets (экспорт в xlsx) | `docProps/app.xml` **отсутствует**; одиночный `CR` после декларации; GP flags `0x0808` (UTF-8 + descriptor) |
| `libreoffice` | 4 xlsx | LibreOffice 24.2.7.2 (Linux x86-64), исходник создан openpyxl | `<Application>LibreOffice/24.2.7.2$Linux_X86_64…`, `dc:creator = openpyxl` |
| `40250030` | 1 docx | **КонсультантПлюс, версия 4025.00.30** (отсюда имя файла) | `<Application>КонсультантПлюс Версия 4025.00.30</Application>` |
| `other` | 16 docx | **два разных производителя** — см. ниже | |

Метка `other` в манифесте склеивает две разные вещи, и это стоит развести:

| файлы | producer | признак |
| --- | --- | --- |
| `other_01…04`, `other_08…16` (13 шт.) | **Яндекс Документы** | namespace `xmlns:vyd="http://volga.yandex.com/schemas/document/model"`, атрибуты `vyd:_id`, декларация `<?xml version="1.0" ?>` без `encoding` |
| `other_05…07` (3 шт.) | **Google Документы** (экспорт docx) | каталог `customXML/` (с заглавными), встроенные шрифты `word/fonts/*.ttf`, строка `Google` в частях, одиночный `CR` после декларации |

## 4. Два независимых слоя: XML и контейнер

Важное наблюдение, из-за которого колонка `producer` в манифесте может вводить
в заблуждение. **Кто написал XML и кто написал ZIP — разные субъекты.**

Пример. `excel365_07…11`: XML внутри — от Microsoft Excel (`app.xml` это
подтверждает), но контейнер имеет отпечаток, которого Excel никогда не даёт:

| признак | Excel пишет | в `excel365_07…11` |
| --- | --- | --- |
| `version_made_by` | 45 (0x002D) | **20** (0x0014) |
| GP flags | `0x0006` / `0x0000` | **`0x0008`** |
| `local_extra` | 0 / 264 / 520 (Growth Hint) | **0 во всех записях** |
| DOS-время | 1980-01-01 (`0x0021`) | **`0x0000/0x0000`** — невалидная дата |
| data descriptor | нет | **есть у всех 12 записей** |

То есть эти файлы были **перепакованы** потоковым ZIP-writer'ом уже после
Excel — почтовым сервисом, файлообменником или каким-то нормализатором.
Тот же отпечаток (made_by 20, flags `0x0008`, нулевое DOS-время, descriptor
16 байт) у `gsheets_05`, `word365_03` и всех 16 `other_*`: суммарно
**296 записей в 31 файле**.

Для проекта это хорошая новость: корпус проверяет не только «умеем ли мы
сохранить то, что пишет Office», но и «умеем ли мы сохранить то, во что чужие
инструменты Office превратили». Ровно это и происходит с файлами пользователей.

## 5. Что каким файлом покрыто

Ниже — карта: какая особенность формата встречается только в одном-двух файлах.
Удалить такой файл из корпуса — значит перестать проверять эту особенность.

### 5.1 ZIP-уровень

| особенность | единственный носитель | записей |
| --- | --- | ---: |
| **directory-записи** (имя на `/`, method=0, csize=usize=0) | `40250030_01.docx` | 5 |
| **`internal_attrs = 1`** (флаг «текстовый файл») | `40250030_01.docx` | 16 |
| **`external_attrs = 0x00000020`** (DOS archive) | `40250030_01.docx` | 17 |
| **`external_attrs = 0x41C00010`** (Unix dir 0700 + DOS dir) | `40250030_01.docx` | 5 |
| **`version_made_by = 23`** (0x0017, FAT 2.3) | `40250030_01.docx` | 22 |
| **GP flags `0x0004`** | `40250030_01.docx` | 17 |
| **stored-запись с реальными данными** (method=0, 178 463 байта) | `word365_02.docx`, `word/media/image1.jpeg` | 1 |
| **`version_needed = 10`** | `word365_02.docx` (та же запись) | 1 |
| **`local_extra = 40`** (Growth Hint PadVal 32) | `word365_02.docx`, `customXml/item*.xml` | 2 |
| **`version_made_by = 788`** (0x0314, Unix 2.0) + `external_attrs = 0x81A40000` (0644) | `excel365_05.xlsx` | 12 |
| **смешанные GP flags внутри одного архива** | `40250030_01.docx` (`0x0000`+`0x0004`), `word365_02.docx` (`0x0000`+`0x0006`) | — |
| **смешанные методы сжатия внутри одного архива** | `40250030_01.docx`, `word365_02.docx` | — |
| `local_extra = 264` / `520` (Growth Hint 256 / 512) | excel365_01…04/06, word365_01/02/04/05/06 | 31 / 20 |
| GP flags `0x0808` (UTF-8 + descriptor) | gsheets_01…04, libreoffice_01…04 | 122 |
| `[Content_Types].xml` **не** первой записью | 17 файлов (все gsheets/libreoffice + excel365_07…11 + other_05…07) | — |

Вывод: **`40250030_01.docx` — самый ценный файл корпуса.** Он единственный
носитель шести особенностей ZIP-уровня. `word365_02.docx` — второй по
ценности. Если корпус придётся сокращать, эти два трогать нельзя.

### 5.2 XML-уровень

| особенность | единственный носитель | вхождений |
| --- | --- | ---: |
| **BOM** | `40250030_01.docx` | 16 частей |
| **пробел перед `/>`** (`<w:shd … />`) | `40250030_01.docx` | 181 |
| **пробел перед `>`** | `40250030_01.docx` | 24 |
| **пробелы вокруг `=`** (`w:customStyle = "1"`) | `40250030_01.docx` | 39 |
| **литеральные CR и LF внутри значения атрибута** | `40250030_01.docx` (`w:tooltip`) | 7 и 7 |
| **`&#34;`, `&#60;`, `&#62;`, `&#160;`** (числовые вместо именованных) | `40250030_01.docx` | 44 / 3 / 3 / 1 |
| **`&gt;`** | `libreoffice_04.xlsx` | 1 |
| **декларация `standalone="no"`** | `word365_02.docx` | 2 части |
| **декларация `<?xml version="1.0" ?>`** (без `encoding`) | 13 файлов Яндекс Документов | 156 частей |
| **одиночный `CR` после декларации** | gsheets_01…04, gsheets_05, other_05…07 | 110 частей |
| **два пробела после имени тега** | `<styleSheet  xmlns=` в 6 файлах, `<w:rFonts  ` в `40250030_01.docx` | 31 |
| **`&#xA;` в тексте** | excel365_07…11, gsheets_05 | 127 |
| `<a></a>` вместо `<a/>` | 34 файла | 104 911 |

И здесь `40250030_01.docx` покрывает шесть особенностей единолично. Он же —
единственный файл с BOM.

### 5.3 Чего корпус НЕ покрывает

Честный список дыр. Их закрывают синтетические файлы в
`crates/ooxml/tests/corpus/synthetic/`, а не измерения.

| не покрыто | почему важно |
| --- | --- |
| ZIP64 (>4 GiB, >65 535 записей) | максимум в корпусе — 712 KiB и 39 записей |
| непустой `cd_extra` | во всех 606 записях он пустой |
| непустой комментарий записи или архива | во всех 606 / 43 пустые |
| префикс архива, зазоры между записями, хвост после EOCD | во всех 43 файлах отсутствуют |
| data descriptor **без** сигнатуры `PK\x07\x08` | все 418 — с сигнатурой |
| data descriptor с 8-байтными полями (ZIP64) | ни одного |
| extra-поля с id, отличным от `0xA220` | других не встречено |
| имена записей не в ASCII | все 88 имён ASCII |
| одинарные кавычки в атрибутах | 0 из 648 183 |
| комментарии, CDATA, PI (кроме декларации), DOCTYPE | 0 частей из 569 |
| `&lt;`, `&apos;` | 0 вхождений |
| кодировка, отличная от UTF-8 | 0 частей |
| шифрование, многотомные архивы | вне области проекта |

## 6. Как пересобрать корпус

Корпус не «генерируется» — он собирается из настоящих документов. Процедура:

1. **Собрать файлы.** Взять `.xlsx` и `.docx`, которые реально ходили по почте
   и через веб-сервисы: экспорт из Google Sheets/Docs, файлы из Яндекс
   Документов, выгрузки из отраслевого ПО (в нашем случае — КонсультантПлюс),
   документы, пересохранённые LibreOffice. **Не** ограничиваться свежими
   файлами прямо из Office: они самые «чистые» и проверяют меньше всего.

2. **Разложить по каталогам** `xlsx/` и `docx/`, переименовать в
   `<producer>_<NN>.<ext>`. Метка producer'а определяется по §3.

3. **Пересобрать `MANIFEST.tsv`.** Колонки `sha256`, `entries`, `made_by`,
   `flags` считаются побайтовым разбором ZIP — не через `zipfile` Python и не
   через любую другую библиотеку: они прячут именно те поля, ради которых всё
   и делается (`local_extra` против `cd_extra`, нулевые crc/размеры при бите 3,
   `version_made_by`).

4. **Перепроверить числа в документации.** Все таблицы в `zip-fidelity.md`,
   `dom-invariants.md` и §5 этого файла — измерения конкретной выборки.
   После смены корпуса они становятся неверными и обязаны быть пересчитаны,
   иначе документ превращается из источника истины в набор преданий.

5. **Проверить покрытие по §5.3.** Если новый корпус потерял, например,
   единственный файл с directory-записями, покрытие надо восстановить —
   либо новым реальным файлом, либо синтетическим в `synthetic/`.

6. **Прогнать оракул.** `cargo test --test soffice -- --ignored` с
   `OOXML_SOFFICE`, указывающей на бинарь LibreOffice. Если какой-то файл
   корпуса не открывается даже LibreOffice, он битый и в корпусе ему не место.

Минимальный критерий пригодности нового корпуса: он должен содержать хотя бы по
одному носителю каждой особенности из §5.1 и §5.2. Проще всего это проверить,
прогнав те же разведочные скрипты и сравнив распределения.
